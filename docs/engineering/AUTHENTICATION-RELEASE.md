## Account eligibility matrix

Every allowed state requires a confirmed email and membership in the approved deployment policy. Phone OTP is deferred. Authentication alone grants no KYC, wallet or financial permission.

| Account status | Recommended browser authentication |
|---|---|
| REGISTERED, CONTACT_UNVERIFIED | Deny until email confirmation. |
| CONTACT_VERIFIED | Allow when selected by the release. |
| KYC_REQUIRED, KYC_PENDING | Allow when selected so the customer can complete or monitor KYC. |
| KYC_APPROVED | Allow when selected. Financial actions still need their own checks. |
| KYC_REJECTED, RESTRICTED | Deny. A remediation-only journey requires a separate Product/Compliance decision. |
| SUSPENDED, CLOSED | Deny. A prior cookie cannot restore access. |

## Phase 4 integration

The integration contract for Phase 4 is to mount the customer router with `auth.protect(routes)`. Extract `deypay_api::login::AuthenticatedCustomer` in the handler. Use `customer.id()` for ownership and `customer.account_status()` for the status at admission. Ignore client-supplied identity fields and headers. A missing, expired, rotated or revoked cookie returns 401. An unsafe method requires exactly one matching HTTPS Origin. Handlers must enforce KYC policy and recheck time-sensitive authorization in the transaction performing the protected write.

## Database security review and rollout gate

The sandbox migration pins each privileged routine's search path and qualifies relations. Its credential lookup and issuer both grant execution to the general API database role. That role can obtain a verified sandbox customer's PHC through the lookup. The issuer compares a caller-supplied PHC to that same record, which does not establish that the caller checked the password. The general API role can also insert arbitrary action names using its existing audit insert grant. These are blockers for hosted authentication. Expanding the customer-state predicate in these routines would expand the exposure. [Sandbox migration](../../backend/migrations/202611250501_sandbox_login_sessions.sql) · [Sandbox grants](../../infrastructure/postgres/sandbox-auth-grants.psql) · [General role grants](../../infrastructure/postgres/phase-two-grants.psql)

The proposed successor uses a dedicated execute-only runtime identity, verifier-signed assertions scoped to their purpose, release, credential snapshot and session digest, and atomic replay protection. Verification secrets belong to the verifier and migration owner. No key belongs in Git, pooled application logs or runtime-readable tables. A stolen database login alone should be unable to mint a session or fabricate an authoritative authentication event. Compromise of the verifier process, migration owner or key authority remains an incident requiring key retirement and session invalidation. The shared migration, role, extension location, and grants require coordinator review. PostgreSQL recommends a trusted search path and revoking default PUBLIC execution in the transaction that creates privileged functions. [PostgreSQL CREATE FUNCTION](https://www.postgresql.org/docs/16/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY) · [PostgreSQL pgcrypto](https://www.postgresql.org/docs/16/pgcrypto.html)

Before a hosted rollout, Platform must provision isolated API, verifier and migration credentials, verify PostgreSQL server identity, terminate browser traffic at a trusted HTTPS ingress, and prohibit direct public access to the API listener. Security and Operations must test the approved admission and Argon2 budgets under concurrent valid and invalid logins, verify the secret mount, and validate the release on every replica. Rehearse a release retirement and verify that old sessions remain denied across replicas. Compliance must approve audit retention, access and incident alerting. Never include credentials, raw email, cookies, assertions or PHCs in telemetry. A denied request should expose only a generic error.
