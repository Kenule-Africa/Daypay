# Customer authentication release and integration

## Decision register

An engineering fixture exercises a policy. Only Product, Security and Compliance can supply approvals for their respective controls. The verifier and reader support local, test, staging and production environments. The migration installs no release, key or policy values. Hosted activation requires a database-owner-installed release tied to the deployment environment and formal approvals.

## Account eligibility matrix

Every allowed state requires a confirmed email and membership in the approved deployment policy. Phone OTP is deferred. Authentication alone grants no KYC, wallet or financial permission.

| Account status | Recommended browser authentication |
|---|---|
| REGISTERED, CONTACT_UNVERIFIED | Deny until email confirmation. |
| CONTACT_VERIFIED | Allow when selected by the release. |
| KYC_REQUIRED, KYC_PENDING | Allow when selected so the customer can complete or monitor KYC. |
| KYC_APPROVED | Allow when selected. Financial actions still need their own checks. |
| KYC_REJECTED, RESTRICTED | Deny. A remediation-only journey requires a separate Product/Compliance decision. |
| SUSPENDED, CLOSED | Deny. A prior cookie cannot restore access. |

## Phase 4 integration

The integration contract for Phase 4 is to mount the customer router with `auth.protect(routes)`. Extract `deypay_api::login::AuthenticatedCustomer` in the handler. Use `customer.id()` for ownership and `customer.account_status()` for the status at admission. Ignore client-supplied identity fields and headers. A missing, expired, rotated or revoked cookie returns 401. An unsafe method requires exactly one matching HTTPS Origin. Handlers must enforce KYC policy and recheck time-sensitive authorization in the transaction performing the protected write.

## Runtime trust boundaries

| Principal | Credentials and access | Effect of compromise |
|---|---|---|
| General API, `deypay_app` | Its own database login and a release UUID. The session reader calls `auth_principal` with a presented token digest and returns the current customer and status. | Can impersonate customers whose live bearer cookies it intercepts and misuse its ordinary application permissions. Its database identity cannot look up password hashes, mint or rotate sessions, retrieve session digests, read release keys, or insert authoritative authentication events. |
| Verifier, `deypay_auth` | Separate listener, OS/container identity, database login and secret-manager mount. It exposes login, refresh, liveness and readiness. Its only database capabilities are the named authentication functions. | Database credentials alone permit admission consumption and availability disruption. A compromised verifier **process** can see submitted passwords and use its signing authority. Treat that as an authentication-wide incident. |
| Protected database owner, `deypay_auth_owner` | NOLOGIN. Owns the release tables and authentication functions. Has narrowly scoped reads and row-lock privileges on the identity and credential records, session write privileges and audit append privileges. | A principal permitted to assume this role can change the authority. Only the controlled migration/DB administration identity may assume it. |
| DBA and secret administrator | Provision roles, keys and releases. Protect database backups to the same standard. | Database-owner or verifier-secret compromise requires incident response, key replacement and session invalidation. |

At the HTTPS ingress, route exactly `POST /api/v1/auth/login` and `POST /api/v1/auth/refresh` directly to the `deypay-auth` deployment. Other API traffic goes to `deypay-api`. Disable body and Cookie/Set-Cookie logging throughout the path. Give the processes independent service accounts, filesystem access, network policies and secret-manager permissions. Keep the verifier mount, database credentials, process environment and container-management interfaces inaccessible to the general API. Merely using different PostgreSQL users in one process does not establish isolation. Keep listeners private. Hosted SQLx connections use server-identity-verifying TLS.

## Database installation and activation

1. Before SQLx migrations, run `infrastructure/postgres/auth-roles.psql` once per cluster as the DBA. New disposable Compose clusters do this automatically. Existing clusters require this step explicitly. The script creates `deypay_auth` and `deypay_auth_owner` with NOLOGIN and zero elevated attributes. For a verifier deployment, provision LOGIN and separate credentials for `deypay_auth` using the secret manager. Keep `deypay_auth_owner` NOLOGIN with no elevated memberships. Both runtime roles must be ordinary NOSUPERUSER, NOCREATEROLE, NOCREATEDB, NOREPLICATION, NOBYPASSRLS roles. Neither may inherit or switch into the other, a database owner or privileged built-in role. Use a separate protected migration identity. Never pass the migration login to either runtime.
2. Apply SQLx migrations. `202611250502_authentication_releases.sql` retires all legacy sandbox functions and revokes legacy sessions with audit evidence. It installs pgcrypto in the restricted `auth_crypto` schema. A pre-existing installation in another schema requires DBA coordination before migration. The migration is transactional. The next migration, `202611250503_authentication_ownership.sql`, enforces one-use release keys and checks the non-login owner. Apply `infrastructure/postgres/auth-grants.psql` after migrating each database using an administrator authorized to transfer ownership. The script transfers only auth-owned objects, installs prerequisite privileges for the definer, checks the effective grants and commits them atomically. Preserve the ordinary Phase 2 and independently managed KYC grants.
3. Under change control, insert **one active release** into `identity.auth_policy` with a fresh UUID, exact environment, HTTPS browser origin, explicit allowed state array, measured Argon2 memory/passes/lanes/slots, idle and absolute deadlines, assertion lifetime (1–60 seconds), total/per-identifier minute budgets, and Product, Security and audit approval references. Provision a unique 32-byte random key using secret-manager-backed bound parameters. Disable statement parameter logging for this provisioning connection and protect backups. Store the matching 64-hex-character key in a verifier-only read-only mount. Never put an actual key in a migration, shell history, manifest or PR.
4. Set `APP_ENV`, `DEYPAY_LOGIN_MODE=enabled`, `DEYPAY_AUTH_RELEASE`, `DATABASE_URL`, `DB_MAX_CONNECTIONS` and the private `API_BIND_ADDR` independently for each deployment. The general API alone needs `DEYPAY_LOGIN_ORIGIN`. The verifier alone needs `DEYPAY_AUTH_SIGNING_KEY_FILE`. Both release UUIDs must match. Use the real runtime login as the hosted PostgreSQL session user. Verify both readiness endpoints before routing traffic.
5. For rotation, stop admitting new logins at ingress, retire the old release and install the new one in one DBA transaction, roll replicas to the matching key and release, verify readiness, then resume traffic. Retirement revokes old sessions, prevents reactivation, and rejects old proofs. Expect customers to sign in again. Restrict access to retired database key material and backups under the approved retention policy.

## Issuance, admission and audit

After Argon2id verification, the verifier signs a versioned, purpose-separated HMAC-SHA-256 message containing the release, issuance time, customer ID, exact email fingerprint, checked credential fingerprint, new random session digest and any previous digest. PostgreSQL verifies the signature and freshness, rechecks email proof, status and the locked credential, and atomically consumes the new digest as the 256-bit replay identifier. Its receipt survives token rotation and remains until the proof has expired. Session creation, replacement, login success, session issuance and mandatory audit writes commit together. SQL uses bound values, schema-qualified names and pinned function search paths. PUBLIC execution is revoked inside the migration. The protected-audit trigger checks the effective database writer. [PostgreSQL CREATE FUNCTION](https://www.postgresql.org/docs/16/sql-createfunction.html#SQL-CREATEFUNCTION-SECURITY) · [PostgreSQL pgcrypto](https://www.postgresql.org/docs/16/pgcrypto.html)

All verifier replicas share a locked PostgreSQL minute window. The first admission reserves deployment capacity before reading the body. The second limits the normalized identifier before Argon2 work. A release-keyed HMAC conceals stored identifiers. Both the total number of accepted identifier admissions and the number of allocated identifier rows per window are bounded by the deployment cap. The next admitted request in a new minute clears prior identifier counters and expired issuance receipts. A calendar-window boundary can admit two adjacent bursts. Benchmark thresholds and provision the per-verifier CPU/memory budget for that behavior. A full budget yields 429. Loss of the mandatory store yields 503. Configure ingress limits for connection and transport-level abuse.

Validation uses the database clock after obtaining the session lock. A status transition between approved states requires token refresh before the next protected request. Withdrawal of email proof, a change of verified email, entry into a disallowed state or release retirement invalidates existing sessions. Refresh cannot extend the original absolute deadline. Monitor database latency, availability, saturation, audit-write failures, rejection volume and clock synchronization. Retention, alert thresholds, trusted ingress and external secret custody remain deployment controls.
